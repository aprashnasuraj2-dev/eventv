Why this page exists

Google I/O moves faster than the “keynote recap” format can handle.

A keynote can mix research direction, product demos, private previews, public previews, developer betas and generally available releases in the same hour. Those states are not equivalent. For a production team, the important question is rarely “what was announced?” It is usually what changed, who can use it, under what terms, on which version, and when does it become safe to adopt?

Gemini API

Interactions API is the current recommended path for new projects

Google’s official Gemini API documentation says the Interactions API is generally available and recommended for all new projects as of June 2026. It describes the older generateContent API as legacy but still fully supported, and says new models, multimodal capabilities, tools and agentic features will launch on Interactions API going forward.

Engineering action now: inventory which production services call generateContent versus Interactions API, record model IDs, quotas, storage behavior and fallback paths before any 2027 announcement.

I/O content shape

2026 covered multiple developer surfaces

The official 2026 I/O archive groups on-demand content under AI, Android, Chrome and Cloud and retains separate Google and Developer keynotes. That is useful as a research map for where to watch in 2027, but it is not a guarantee that the 2027 program will use the same tracks or format.

Engineering action now: establish owners for each platform your product actually depends on, instead of assigning one person to “watch I/O.”

Counterexample: a major keynote announcement can be irrelevant to your stack, while a small documentation change published outside the keynote can be operationally urgent. Event prominence ≠ migration priority.

Developer workflow

A practical I/O verification sequence

  1. Freeze a pre-event baseline.Record SDK/API versions, model IDs, quotas, pricing pages, current deprecation notices, test devices and rollout channels you actually use.
  2. Capture the primary announcement.Save the Google blog, developer documentation, release note or official session page—not only a social post or news summary.
  3. Label maturity precisely.Demo, research, private preview, public preview, beta, GA and rollout-in-progress should remain separate states.
  4. Check eligibility.Account type, country, device, SDK, browser channel, billing plan and allowlist restrictions can change whether “available” applies to you.
  5. Check economics and limits.Pricing, quotas, rate limits, context limits, storage/retention, free-tier rules and paid-plan availability belong in the migration record.
  6. Test rollback.For production changes, prove that you can revert model/API/SDK behavior before adopting an I/O-announced feature under deadline pressure.

Which phones will get the Android preview announced at I/O 2027?

What will Google announce about Gemini in 2027?

Unknown. Current developer documentation, not speculation, is the correct baseline. As of this verification date, Google recommends the Interactions API for new Gemini projects while the older generateContent API remains supported but is described as legacy.

Does “announced at I/O” mean I can use it in production?

No. An announcement may describe a demo, preview, beta, staged rollout or generally available feature. Even GA can have account, region, quota, pricing or compatibility constraints. Track maturity and eligibility separately.

Freshness & conflict policy

How this page should change when Google publishes 2027 details

2. Preserve conflicts

Do not convert “coming later this year” into a release date. Do not turn a demo into availability.

Once a real date exists, review schema, timezone copy, social image, FAQ and any historical comparison that could become stale.
